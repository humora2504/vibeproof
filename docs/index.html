Then fix it, and prove you fixed it

Finding the holes is the easy half. The hard half is writing correct policies for every table, remembering that table privileges are checked before policies are, and then knowing it worked rather than hoping. The dashboard showing a green shield is not proof.

The Fix Pack reads your migrations, works out who owns each row, and writes:

rls_policies.sql

Policies for every table, matched to your ownership columns: user-owned, organisation-owned via a membership table found in your own schema, or self-owned by a key referencing auth.users. Enables and forces Row Level Security and revokes the table privileges from anon that people forget. Your existing policies are left in place and listed for review, because a policy you wrote deliberately is not ours to delete. One transaction.

rls_tests.mjs

The part nobody else gives you. It creates two throwaway users, writes a row for one, and then checks from outside that an anonymous visitor is refused, that the other user cannot read, change or delete that row, and that the owner still can. Then it deletes the test users.

REPORT.md

Every table, whether Row Level Security is on today, which column it assumed is the owner and how confident it is. Tables where no owner could be identified are set to deny everything and listed for you to decide, because a table that errors is safer than one that leaks.

ci.yml + 4 playbooks

A GitHub Actions gate that fails the build on a critical or high finding, so this cannot regress. Plus runbooks for rotating a leaked key in the right order, locking down storage, hardening server actions, and what to do in the first hour after a leak.

Questions

Does anything leave my machine?

No. The scanner and the generator both run locally and make no network requests. You can read the source of the scanner before you run it. Findings print redacted evidence, so a key it finds is never echoed in full.

Will it break my app?

It can, and that is deliberate for one case. Turning on Row Level Security denies everything until a policy allows it, so a table that was silently world-readable will start returning nothing until the right policy is in place. That is the point.

The generated SQL is a single transaction with comments, meant to be read before it is run, and the report tells you which tables it was unsure about. Apply it to a branch or a copy first. Tables where no owner column could be found are set to deny everything and listed for your decision rather than guessed at.

What if it cannot find my schema?

It reads SQL migrations from the usual places: supabase/migrations, migrations, db/migrations, prisma/migrations, drizzle, sql and database. If your schema only exists in the Supabase dashboard, export it first with supabase db dump --schema public -f supabase/migrations/000_schema.sql and run it again. If that still does not work, ask for a refund.

Is this a security certification?

No, and anyone selling you one for $19 is lying. It checks a specific, common and damaging set of mistakes: access to your tables and your storage. It does not review your application logic, your dependencies, or your infrastructure, and a clean result is not a guarantee that you are secure.

Firebase, Prisma, Drizzle, other databases?

The free scanner checks Firebase rules, Firestore and Realtime Database, alongside Supabase and Postgres. The Fix Pack generates Postgres Row Level Security, so it applies to Supabase and to any Postgres database. Prisma and Drizzle projects work as long as their SQL migrations are in the repository. If you use Firebase only, the free scanner is the useful half and the pack is not for you.

Row Level Security broke my app. Is that this tool's fault?

Turning it on denies access until a policy allows it, so a table that was silently world-readable stops returning rows until the right policy exists. That is the protection working, not a fault. The error you will see is new row violates row-level security policy, and that page explains the four causes in the order worth checking.
